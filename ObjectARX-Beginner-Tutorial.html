ObjectARX Training

Introduction

Welcome! This tutorial teaches you how to write your first ObjectARX plug-in for AutoCAD — twice.

What is ObjectARX? It is the C++ toolkit (SDK) for building programs that run inside AutoCAD. A finished plug-in is an .arx file — really a Windows DLL with a different extension. AutoCAD loads it, and your code can add commands, draw objects, and react to what the user does.

You'll do the same small task two ways, so you understand both the fundamentals and the fast path:

  • Lesson 1 — From scratch. You set up an empty C++ project by hand and wire up every setting yourself. This is slower, but it shows you exactly what an ObjectARX project is.
  • Lesson 2 — With Claude Code. You use an AI assistant and a ready-made "wizard skill" to generate the same kind of project in seconds — then focus on your code instead of the plumbing.

Both lessons end the same way: you type a command in AutoCAD and see a message appear. Start by installing the tools.

Before you begin

Getting Set Up — What to Download

You need three things installed. Install them in this order.

1. AutoCAD 2027

The host program your plug-in runs inside. Download and install it from your Autodesk account (manage.autodesk.com), or get a free version through the Autodesk Education program if you are a student or educator. AutoCAD is 64-bit only — there has been no 32-bit AutoCAD since 2020.

2. The ObjectARX 2027 SDK

This is the free package of C++ header files (.h) and libraries (.lib) you build against. Get it from the Autodesk Platform Services developer page for AutoCAD: aps.autodesk.com/developer/overview/autocad. Go to the APIs section and click on the ObjectARX SDK hyperlink, click on "View license agreement" and proceed with further steps. Unzip it to a simple path with no spaces, for example C:\ObjectARX 2027\. Remember this location — you'll point Visual Studio at it.

Tip. Inside the SDK you'll mainly use two folders: inc (and inc-x64) for headers, and lib-x64 for libraries.

3. Visual Studio 2026

The editor and C++ compiler (the "IDE"). The free Community edition is fine. During installation, tick the "Desktop development with C++" workload — that's the part that gives you the C++ compiler ObjectARX needs.

Lesson 1 · No AI, no wizard

Build an ObjectARX App From Scratch

In this lesson you create a new ObjectARX project in Visual Studio 2026 completely by hand and build your first application. There is no template to start from — you'll do every step yourself, so you learn what each piece is for.

The goal is small on purpose: a command called HELLO that prints "Hello World!" on the AutoCAD command line.

Why do it by hand first. Doing it once by hand is how the settings "click." Lesson 2 shows how the wizard automates all of this for you.

Step 1 — Create the project

  1. In Visual Studio, choose Create a New Project…
  2. Search for and select the "Windows Desktop Wizard" template (a plain C++ template), then click Next.
  1. Enter a project name — this tutorial uses Step01 — pick a location, and click Create.
  2. In the "Windows Desktop Project" dialog, set Application type to Dynamic Link Library (.dll).
  1. Leave the other options unticked and click OK to create the project.

You now have an empty DLL project. On its own it knows nothing about AutoCAD — the next two steps fix that by telling it where the ObjectARX SDK is.

Step 2 — Compiler settings

Open Solution Explorer (menu View → Solution Explorer, or the shortcut Ctrl+Alt+L). Select the Step01 project, right-click it, and choose Properties to bring up the project's property pages. At the top, set Configuration to All Configurations so your changes apply to both Debug and Release.

  1. C/C++ → General → Additional Include Directories: add the SDK's include folders, e.g. C:\ObjectARX 2027\inc and C:\ObjectARX 2027\inc-x64. Also set Warning Level to Level 1 to hide warnings that don't matter here. Click OK to apply and close.
  2. C/C++ → Code Generation → Runtime Library: choose Multi-threaded DLL (/MD).
  3. C/C++ → Preprocessor → Preprocessor Definitions: remove the _DEBUG symbol if present.
  4. Configuration Properties → General → Platform Toolset: select v145 (the toolset that matches Visual Studio 2026 / AutoCAD 2027).

Alternative for the include/library paths. Instead of the Additional Include Directories field, you can set the same paths under Configuration Properties → VC++ Directories: use Include Directories for the SDK's inc folders and Library Directories for its lib-x64 folder.

The most important rule in all of ObjectARX: always use /MD (Multi-threaded DLL) — even in Debug builds. AutoCAD itself is always a Release program, so your plug-in must match it. Using /MDd causes crashes and "heap corruption." This is why you remove _DEBUG above.

Step 3 — Linker settings

  1. Linker → Input → Additional Dependencies: add the core ObjectARX libraries: 
    rxapi.lib;acdb26.lib;acge26.lib;acad.lib;ac1st26.lib;accore.lib

About that "26" in the library names. The number tracks the AutoCAD release (2026 → 25, 2027 → 26). If a library name isn't found, open your SDK's lib-x64 folder and use the exact names you see there.

  1. Linker → General → Additional Library Directories: add the SDK's library folder, e.g. C:\ObjectARX 2027\lib-x64.
  2. Linker → General → Output File (or Advanced → Target File Extension): change the output extension from .dll to .arx.

Your project settings are now complete. Next, the actual code.

Step 4 — Add the code

  1. From the Project menu, choose Add New Item… (shortcut Ctrl+Shift+A).
  2. In the "Add New Item" dialog, select C++ File (.cpp).
  3. Enter HelloWorld in the Name: box and click Add.

First, include the headers you need. aced.h gives access to AutoCAD's editor services; rxregsvc.h declares the ObjectARX registration utilities; tchar.h provides the _T() text macro:

#include "pch.h"
#include "tchar.h"
#include <aced.h>
#include <rxregsvc.h>

Declare the three functions you'll write — one to run when AutoCAD loads the app, one when it unloads it, and one that does the actual work:

void initApp();
void unloadApp();
void helloWorld();

initApp() registers a new command with AutoCAD. Registering a command gives AutoCAD a new "entry point" into your app — the word the user types:

void initApp()
{
    // register a command with the AutoCAD command mechanism
    acedRegCmds->addCommand(_T("HELLOWORLD_COMMANDS"),
                            _T("Hello"),      // global (untranslated) name
                            _T("Bonjour"),    // local (translated) name
                            ACRX_CMD_TRANSPARENT,
                            helloWorld);      // function to call
}

The arguments are: the command group name, the global command name, the localized name, a flag (ACRX_CMD_TRANSPARENT means it can run while another command is active), and the function to call when the command runs.

unloadApp() removes that command group when AutoCAD unloads the app — you must clean up the entry points you added:

void unloadApp()
{
    acedRegCmds->removeGroup(_T("HELLOWORLD_COMMANDS"));
}

helloWorld() is the command itself. acutPrintf() is ObjectARX's version of C's printf, aimed at the AutoCAD command line:

void helloWorld()
{
    acutPrintf(_T("\nHello World!"));
}

Finally, the single most important function in any ObjectARX app: acrxEntryPoint(). Because a plug-in is a DLL (it has no main()), AutoCAD calls this function to send it messages — "you are being loaded," "you are being unloaded," and so on:

extern "C" AcRx::AppRetCode
acrxEntryPoint(AcRx::AppMsgCode msg, void* pkt)
{
    switch (msg)
    {
    case AcRx::kInitAppMsg:
        acrxDynamicLinker->unlockApplication(pkt);  // allow unloading
        acrxRegisterAppMDIAware(pkt);
        initApp();
        break;
    case AcRx::kUnloadAppMsg:
        unloadApp();
        break;
    default:
        break;
    }
    return AcRx::kRetOK;
}

When AutoCAD loads the app (kInitAppMsg), unlock it so it can be unloaded later, mark it MDI-aware, and register the command. When AutoCAD unloads the app (kUnloadAppMsg), remove the command.

Step 5 — The .def file

AutoCAD can only find acrxEntryPoint() if the DLL exports it. The simplest way is a module definition (.def) file.

  1. From the Project menu, choose Add New Item… (Ctrl+Shift+A).
  2. In the "Add New Item" dialog, select Module-Definition File (.def).
  3. Enter ArxProject in the Name: box and click Open.

Clear any auto-generated content and add the following to the new file. Every ObjectARX application must export at least these two functions — acrxEntryPoint and acrxGetApiVersion:

EXPORTS
    acrxEntryPoint      PRIVATE
    acrxGetApiVersion   PRIVATE

Note. You may see linker warning LNK4099 for some libraries during the build. It's harmless here — you can ignore it.

Step 6 — Build & run

Set the configuration to x64 and build with Build → Build Solution (Ctrl+Shift+B). If you followed along, you'll get 0 errors and your plug-in appears as Step01.arx in the project's x64 output folder.

Now load and run it in AutoCAD. Start AutoCAD 2027, open any drawing, and load Step01.arx using any of these methods:

  1. Drag the file from Windows Explorer into the AutoCAD window.
  2. Use the AutoCAD ARX command's Load option at the command line.
  3. From the Tools menu, choose Load Application….
  4. Type APPLOAD, browse to Step01.arx, and click Load.

Once loaded, type HELLO and press Enter. You'll see Hello World! printed on the command line. (Typing BONJOUR works too — that was the localized name.)

That's a complete ObjectARX application, built entirely by hand. Notice how much of the work was settings and plumbing, not your actual idea. Lesson 2 removes that busywork. Stuck anywhere above? Compare with the solved project: Solutions\Lesson1_Solved.zip.

Lesson 2 · The fast path

Do It Faster with Claude Code

As you just saw, creating an ObjectARX application by hand is a lot of careful clicking. In this lesson you'll get the same kind of project in seconds using Claude Code and a ready-made wizard skill.

We won't repeat Lesson 1 here. The ObjectARX ideas — commands, acrxEntryPoint(), /MD, the .arx output — are exactly the same. This lesson focuses only on the tools and on what the generated project gives you on top of the hand-built one.

Step 1 — What is Claude Code, and how to install it

Claude Code is an AI assistant that runs in your terminal. Unlike a chat window, it can actually work on your computer — read and write files, run commands, and build projects — while asking your permission before anything risky. You tell it what you want in plain English and it does the steps.

Install it

  1. Open PowerShell (press the Windows key, type PowerShell, Enter).
  2. Install Claude Code using the official native installer — no Node.js required, and it keeps itself updated automatically: 
    irm https://claude.ai/install.ps1 | iex
  1. Move into a working folder and start it by typing claude: 
    cd C:\Users\you\source\repos
claude
    The first time, it will walk you through signing in.

Prefer npm? npm install -g @anthropic-ai/claude-code still works and installs the same tool, but it requires Node.js 22+ and doesn't auto-update — you'd run claude update yourself. The native installer above is Anthropic's recommended method.

Two handy habits inside Claude Code: commands that start with / (a "slash command") run a skill; and a line that starts with ! runs a shell command yourself, e.g. !dir.

Step 2 — Get the ObjectARX wizard skill

A skill is a small folder of instructions and scripts that teaches Claude Code how to do a specialized task well. Think of it as a plug-in for the assistant. When a skill is installed, you trigger it with a slash command.

The one you want is acad-arx-wizard. It replaces the old (and, in Visual Studio 2026, broken) ObjectARX project wizard with scripts that generate the same project files.

Install the skill

  1. Open the skill in your browser: github.com/autodesk-platform-services/skills → skills/acad-arx-wizard. Go through its README file in detail to understand what it does before installing it.
  2. Download that repository (green Code → Download ZIP button) and unzip it.
  3. Copy the acad-arx-wizard folder into your personal Claude Code skills folder: 
    C:\Users\<you>\.claude\skills\acad-arx-wizard
    That folder is exactly where this skill is installed on this machine.
  4. Windows blocks PowerShell scripts by default, and every wizard action runs one. In PowerShell, run this once to allow locally-installed scripts: 
    Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
  5. Start (or restart) Claude Code. Type / and you should see acad-arx-wizard in the list of available skills.

How to tell it worked: inside Claude Code, run /acad-arx-wizard. If the skill is installed, Claude greets you and asks which kind of project or class you want.

Faster install, if you already have Node.js. The skill's repository also supports installing it with a single command instead of the manual download-and-copy above: npx skills add autodesk-platform-services/skills --global --skill acad-arx-wizard. This needs Node.js v16.7+ (for the install only) — the manual method above works without it.

Good to know about the skill

Why this skill exists. The classic .vsz / VsWizardEngine wizard (File → New → ObjectARX) is broken in Visual Studio 2026 — a known VS regression (see MS Developer Community #11071541). This skill replaces it for AutoCAD 2027 / VS 2026, running the same kind of generator, so what you get is a normal, standard ObjectARX project. VS 2022 isn't affected by this bug; if you're on VS 2022 you can keep using the original ObjectARX-Wizards installer instead.

It's safe. The skill only writes files into the folder you choose, and Claude Code asks your permission before running anything. It doesn't touch AutoCAD's settings; the one-time PowerShell execution-policy change in Step 2 above is the only Windows-level change, and it's limited to your user account.

Which project type? arx vs dbx vs crx

When you ask for a project, the skill can make three kinds. For your first plug-ins you want arx.

The simple prompt in the next step is enough to start, but the skill accepts more options — just mention them in plain English:

Under the hood (and when things go wrong). A skill is just a folder you can open: SKILL.md (instructions), scripts/ (the generators), templates/, and docs/. Two of those docs are worth knowing about — docs/arx-dev-guide.md explains the build settings, and docs/learnings.md collects real-world build/link gotchas. If a build ever fails, check there before panicking. To update the skill, re-download its folder from the GitHub repo.

Step 4 — What the skill's project gives you (beyond Lesson 1)

The hand-built project in Lesson 1 was deliberately bare. The generated HelloArx project is a more realistic starting point. The extras worth knowing about:

What you getWhy it helps

Auto-registered commands via the ACED_ARXCOMMAND_ENTRY_AUTO(...) macro No more writing initApp()/unloadApp() by hand — add a function, add one macro line, done.

In short: the generated project already has everything Lesson 1 set up by hand, plus the extras above. To add your own command you now just write a function and register it with one macro line:

static void AdskMyGroupHello()
{
    acutPrintf(ACRX_T("\nHello, ObjectARX!"));
}
// ...and at the bottom of the file:
ACED_ARXCOMMAND_ENTRY_AUTO(CHelloArxApp, AdskMyGroup, Hello, Hello, ACRX_CMD_MODAL, NULL)

Naming rule (same idea as Lesson 1). The function name is the command group + the command name: group AdskMyGroup + command Hello → AdskMyGroupHello.

If MYCOMMAND runs with no errors (AutoCAD just returns to a blank command line), the plug-in loaded and works — same underlying proof as Lesson 1's HELLO, you just don't get a printed message yet, because the stub body is empty.

▶ Next: Lesson 3 — Getting input and selecting entities
Lesson 3 · Talking to the user

Getting Input & Selecting Entities

So far your commands just printed a message. Real commands ask the user for something — a number, a choice, a point, or an object in the drawing. In this lesson you'll add two commands to the HelloArx project from Lesson 2 and learn ObjectARX's input and selection functions.

Objectives

  1. MYINPUT — demonstrate input functions:
    1. Ask for an integer, but disallow negative and zero values.
    2. Ask for a real number, but also accept the keywords PI, A, B, C — defaulting to C if the user just presses Enter. The value becomes 3.14 for PI, 10.0 for A, 11.0 for B, 12.0 for C.
    3. Handle the user pressing Esc gracefully.
    4. Print the integer and the real value on the command line.
  2. MYSELECT — demonstrate entity selection:
    1. Ask the user to select a single entity.
    2. If one is selected, show its Object ID (the first element of the returned ads_name data type).

The functions you'll use

ObjectARX gives you a family of acedGetXxx input functions and a set of selection functions. The full list is in the ObjectARX Help; here are the ones relevant to this lesson:

FunctionWhat it does
acedInitGetSets rules for the next acedGetXxx call (e.g. "no negatives") and registers keywords.
acedGetIntPrompts for an integer.
acedGetRealPrompts for a real (floating-point) number.
acedGetInputRetrieves the keyword the user typed after a "keyword" result.
acedEntSelLets the user pick a single entity in the drawing.

The key idea — return codes. Every acedGetXxx function returns a status code that tells you what the user did: RTNORM (entered a normal value), RTNONE (pressed Enter with no value), RTKWORD (typed a keyword), or RTCAN (pressed Esc). Checking this code is how you handle every case correctly.

Step 1 — Add the two commands

You add commands exactly the way Lesson 2 showed: a function, plus one registration macro line. The quickest route is to ask Claude Code to do it for you — from inside the project, just say:

add two commands to HelloArx: MYINPUT and MYSELECT

Claude edits acrxEntryPoint.cpp, adding a function and an ACED_ARXCOMMAND_ENTRY_AUTO line for each. (You can also add them by hand — the next two steps show the code to put in each function.) The scaffolding looks like this:

// inside class CHelloArxApp { ... }:
static void ADSKArxLesson3_MyInput();
static void ADSKArxLesson3_MySelect();

// at the bottom of the file, next to the HELLO entry:
ACED_ARXCOMMAND_ENTRY_AUTO(CHelloArxApp, ADSKArxLesson3, _MyInput,  MyInput,  ACRX_CMD_MODAL, NULL)
ACED_ARXCOMMAND_ENTRY_AUTO(CHelloArxApp, ADSKArxLesson3, _MySelect, MySelect, ACRX_CMD_MODAL, NULL)

Straight from the ObjectARX training samples. The two functions below are the same functions (logic included) as Autodesk's own Step02_Solved sample in the ObjectARX training materials, renamed to fit this tutorial's own numbering — ADSKArxLesson3_MyInput / ADSKArxLesson3_MySelect. That's also why the group name (ADSKArxLesson3) and global command name (_MyInput / _MySelect) look different from the AdskMyGroup pattern used for MYCOMMAND in Lesson 2 — both are valid, it's just a different sample's naming choice.

Step 2 — The MYINPUT command

Here is the full function. Read it top to bottom — each block matches one objective from the overview.

Heads-up: tchar.h isn't automatic. The skill's template doesn't pull in tchar.h by default — TCHAR/_T() below won't compile until you add #include <tchar.h> yourself, near the top of acrxEntryPoint.cpp (Lesson 4's utility functions will need the same fix).

static void ADSKArxLesson3_MyInput()
{
    int stat, iValue;
    double rValue;
    TCHAR kWord[133];

    acedInitGet(RSG_NONEG | RSG_NOZERO, _T(""));

    if (acedGetInt(_T("\nEnter an integer value: "), &iValue) != RTNORM)
        return;

    rValue = 12.0;
    acedInitGet(RSG_NOZERO, _T("PI A B C"));
    stat = acedGetReal(_T("\nEnter a real value [PI/A/B/C] <C>: "), &rValue);
    switch (stat) {
    case RTCAN: // User termination
        return;
    case RTKWORD: // Got a keyword
        if (acedGetInput(kWord) != RTNORM)
            return;
        if (!_tcscmp(_T("PI"), kWord))
            rValue = 3.14;
        else if (!_tcscmp(_T("A"), kWord))
            rValue = 10;
        else if (!_tcscmp(_T("B"), kWord))
            rValue = 11;
        else if (!_tcscmp(_T("C"), kWord))
            rValue = 12;
        break;
    case RTNONE:
        acutPrintf(_T("\nTake default rValue %lf"), rValue);
        break;
    case RTNORM:
        break;
    default:
        return;
    }

    acutPrintf(_T("\nInteger : %d"), iValue);
    acutPrintf(_T("\nReal    : %lf"), rValue);
}

Three things worth noticing:

  • acedInitGet is "one-shot." Its rules and keywords apply only to the next acedGetXxx call, so you call it again before the real-number prompt — and note the rule changes too: RSG_NONEG | RSG_NOZERO for the integer, just RSG_NOZERO for the real (negative reals are allowed here).
  • Keywords come from a space-separated string. acedInitGet(RSG_NOZERO, _T("PI A B C")) tells AutoCAD those four words are valid answers. When the user types one, acedGetReal returns RTKWORD and you read it back with acedGetInput.
  • Every stat value is handled explicitly. RTCAN (Esc) and the unnamed default case both bail out silently; RTNONE (bare Enter) prints that it's falling back to the pre-set default (rValue = 12.0, i.e. C); RTNORM just falls through, since rValue already holds what the user typed.

Lesson 5 · Storing your own data

Dictionaries & Xrecords

Lesson 4 created graphical objects. This lesson stores non-graphical data — a list of names — inside the drawing itself, so it's saved with the DWG and available every time the file is opened.

Two building blocks make this possible:

  • The Named Objects Dictionary (NOD) — a top-level dictionary that every drawing has, where plug-ins store non-graphical data under named keys.
  • AcDbXrecord — a flexible object for holding arbitrary data. It is a much improved mechanism for storing data than the older (and still used) Extended Entity Data.

Recommended pattern. Rather than dropping items straight into the NOD, the recommended approach is to create your own base-level AcDbDictionary inside the NOD and then populate that with your data. Here you'll create a base-level dictionary keyed ADSK_EMPLOYEE_DICTIONARY to hold employee records, storing each employee as an (empty) AcDbXrecord under the employee's name. Keeping the records together in one dictionary lets you iterate through every employee quickly and easily.

You'll add three commands that manage this employee dictionary:

ADDENTRY

  • Checks whether the base-level dictionary ADSK_EMPLOYEE_DICTIONARY exists in the NOD; if it does not, ADDENTRY creates it.
  • Prompts for an employee name and adds an AcDbXrecord for that employee. If the employee already exists in ADSK_EMPLOYEE_DICTIONARY, the request is ignored.

LISTENTRIES

  • Checks whether the base-level dictionary exists; if it does not, the command stops.
  • Uses an AcDbDictionaryIterator to step through the entries and print the name of every employee stored there.

REMOVEENTRY

  • Prompts the user for an employee name.
  • Checks whether the base-level dictionary exists in the NOD; if it does not, the command stops.
  • Removes that employee's entry if it is present.

The object relationship you're building inside the drawing:

Lesson 8 · Transient reactors

Transient Reactors — Reacting to What the User Does

Every lesson so far added a command the user types. This lesson adds no commands at all — instead it watches AutoCAD's editor and database and reacts when something happens. Reactors come in several flavors:

  1. The database reactor, AcDbDatabaseReactor — monitors events within the scope of the database, such as adding and removing entities.
  2. The editor reactor, AcEditorReactor — monitors events that happen while the user is editing a drawing, such as commands starting and ending, or closing an active session.
  3. The object reactor, AcDbObjectReactor — monitors events specific to a particular entity, such as being opened for modification and notify an application when the entity is modified. .
  4. The document manager reactor, AcApDocManagerReactor — since release 2000, AutoCAD is a multiple document environment. This reactor monitors MDI document-window related events, such as opening, closing, and switching documents in the AutoCAD session. SDI mode events are supported as well.

You already have #4. The acad-arx-wizard skill's ARX template generates DocData.h/.cpp with a global AcApDataManager<CDocData> DocVars — see Step 1. It transparently creates and switches one CDocData instance per open document, which is exactly what a document manager reactor would otherwise be needed for. This lesson only needs you to build the other three reactors.

Objective

This application registers no new commands. It depends on EMPLOYEE block references — the kind you created with Lesson 4's CREATE command. It watches for MOVE, ROTATE, STRETCH, SCALE, or grip-stretch starting on an EMPLOYEE block reference, and if the reference's position (its insertion point) ends up different once the command finishes, resets it back to where it was.

Only position is tracked and restored — not scale, rotation angle, or size. MOVE always changes position, so it's always reverted. SCALE or an in-place ROTATE (about the block's own insertion point) don't change position at all, so there's nothing for the reactor to catch — the entity visibly stays scaled or rotated.

The strategy, in order:

  • An editor reactor (AdkEdEmployeeReactor) watches for one of the five monitored commands starting and ending.
  • An object reactor (AdkEmployeeReactor), attached to every EMPLOYEE block reference, notices when one is opened for modify before the transform happens, and records its object ID and current position.
  • When the command ends, the editor reactor compares each recorded position against the block reference's new position and, if it moved, resets it.
  • A database reactor (AdkDbEmployeeReactor) watches for newly created EMPLOYEE block references and attaches the object reactor to them automatically.

Because a user can apply an edit command to a selection set containing several EMPLOYEE references (and other entities) at once, the tracking data is two parallel arrays: an AcDbObjectIdArray (m_changedObjects) and an AcGePoint3dArray (m_employeePositions) — one entry per block reference currently being watched.

These two arrays are also per-document — each open document needs its own copies, swapped in whenever the active document becomes current. Managing that swap on a document-by-document basis is exactly the job a document manager reactor (reactor #4 above) exists to do; see the tip above for where that's already covered.

  1. If m_doRepositioning is true (via DocVars.docData()), return immediately — this notification is a side effect of our own reset, not a user edit.

  4. Get its block definition and check the name (AcDbBlockReference::blockTableRecord(), then the AcDbBlockTableRecord's name). Return if it isn't "EMPLOYEE".
  5. Append its current position to m_employeePositions (AcGePoint3dArray::append()) and its object ID to m_changedObjects (AcDbObjectIdArray::append()).

Create a Global pointer, created and destroyed the same way as the editor reactor — but with no auto-attach argument, since this reactor is attached per-object, not to the editor. Place this reactor in the "acrxEntryPoint.cpp" file as follows: :

AdkEmployeeReactor *pEmployeeReactor = NULL;

// On_kInitAppMsg():
pEmployeeReactor = new AdkEmployeeReactor();

// On_kUnloadAppMsg():
delete pEmployeeReactor;

One instance, many objects. This single AdkEmployeeReactor instance gets attached to every EMPLOYEE block reference — an AcDbObjectReactor can watch more than one object at a time. You don't need a new instance per entity.

Step 4 — Attach/detach utility functions

No skill needed here — this is plain C++ wiring between the pieces you've already built. Declare both functions in DocData.h (they're free functions, not CDocData members) and implement them in DocData.cpp, right below the CDocData constructor/destructor — declaring them in the header is what lets both DocData.cpp itself (the constructor call below) and acrxEntryPoint.cpp (the unload call) see them.

Note. You attach/detach transient reactors with addReactor() / removeReactor(), and here you're attaching one to every EMPLOYEE block reference — but more than one open drawing can contain EMPLOYEE references. DocVars (Step 1's AcApDataManager<CDocData>) manages one CDocData instance per document, so calling attachEmployeeReactorToAllEmployee() from the CDocData constructor runs it once for every open drawing in the session, and again whenever a drawing is newly created or opened. That's what's responsible for attaching/removing the AdkEmployeeReactor instances correctly, document by document.

Acad::ErrorStatus attachEmployeeReactorToAllEmployee(bool attach)

  1. Get the block table (AcDbDatabase::getBlockTable()).
  2. Get the Model Space record (AcDbBlockTable::getAt(), ACDB_MODEL_SPACE).
  3. Get an iterator over it (AcDbBlockTableRecord::newIterator()).
  4. Walk the entities (AcDbBlockTableRecordIterator::getEntity()). Skip anything that isn't an EMPLOYEE block reference.
  5. For each EMPLOYEE reference: if attach is true, AcDbObject::addReactor() the global pEmployeeReactor; otherwise AcDbObject::removeReactor() it.
  6. Delete the iterator and close every object you opened.

Call this from the CDocData constructor (with attach = true) — it runs once per document, whether that document is newly created, opened, or already open when the app loads.

void detachAllEmployeeReactors()

  1. Get a document iterator (acDocManager->newAcApDocumentIterator()) — acDocManager is the global macro for the AcApDocManager that owns every open document.
  2. Save the current document (acDocManager->curDocument()) so you can restore it after.
  3. Iterate every document, making each one current in turn, and call attachEmployeeReactorToAllEmployee(false) on it.
  4. Restore the document that was current before you started iterating.

Call detachAllEmployeeReactors() when your application unloads — every attached object reactor must be removed, the same golden rule as the editor reactor.

Check the linking. Both functions above reference the global pEmployeeReactor pointer — but it's defined in acrxEntryPoint.cpp (Step 3), not here in DocData.cpp. A different .cpp file can't see another file's global unless it's declared extern somewhere both include — add this to StdAfx.h so DocData.cpp links against it correctly (Step 5's AdkDbEmployeeReactor will need the same declaration):

extern AdkEmployeeReactor* pEmployeeReactor;

This template's constructor takes an AcDbDatabase* pDb = NULL and, if non-null, attaches itself immediately (pDb->addReactor(this)) — matching one instance per document's database. Override objectAppended() from AcDbDatabaseReactor.

objectAppended() — algorithm

  1. Check the appended object is an AcDbBlockReference. Return if not.
  2. Get its block table record (AcDbBlockReference::blockTableRecord()).
  3. Get the record's name and check it's "EMPLOYEE" (AcDbSymbolTable::getName()). Return if not.
  4. Attach the shared pEmployeeReactor object reactor to the newly appended block reference (AcDbObject::addReactor()) — this is how EMPLOYEE references created after the application loads still get watched.

Add a pointer to CDocData, one instance per document:


    AdkDbEmployeeReactor* m_pAdkDbEmployeeReactor;

DocVars.docData().m_pAdkDbEmployeeReactor =
    new AdkDbEmployeeReactor(acdbHostApplicationServices()->workingDatabase());

Step 6 — Build & test

  1. Build Lesson8 (x64 Debug) → AdkLesson8.arx.
  2. APPLOAD it in AutoCAD 2027.
  3. Create some EMPLOYEE block references, same as Lesson 4's CREATE command.
  4. Try MOVE on one — it snaps right back to where it started. The transient reactors are doing their job. SCALE, or ROTATE about the block's own insertion point, will not snap back — only position is tracked, so those are expected to visibly stick. See the Objective above for why.
  5. Save and close the drawing.
  6. Reopen the saved drawing. The EMPLOYEE references can now be moved freely — the reactors were transient; they weren't saved with the drawing.
